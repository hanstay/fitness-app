Hybrid Training Plan · implementation plan

Make the plan read your Hevy history.

A good coach programs the next block from the goal, then from how you're actually performing. We have the goal half. This plan builds the performance half — turning the Hevy export from a throwaway snapshot into a measured record of progression and adherence the model can reason over.

The core change

Stop discarding the history

Today every import collapses to one number per lift and overwrites the last one — so the model can only guess your trajectory. Keep the per-session history and two questions become answerable: are you progressing, and did you follow the plan?

Build order · each part stands alone

Three parts

01

Persist the training historyenabler

A new pure module parses the full export into per-session records and stores them, keyed by a hash of the session time so re-uploads upsert instead of duplicating. The old snapshot keeps working alongside it.

  • New functions/src/lib/hevyAnalyzer.ts — group set-rows by start_time into { date, title, exercises[{ name, sets[] }] }.
  • parseHevyCsv.ts writes users/{uid}/strengthSessions/{id} and still derives current_lifts (backward compatible).
  • firestore.rules — owner-read, Functions-write (mirrors the activities seam).
02

Measure progression — two axesobjective

Strength moves in more than one direction, so we track two independent signals off the history, keyed on Hevy's own exercise names (no matching needed):

  • Intensity — e1RM (Epley w·(1+reps/30)): the strength ceiling. PR + date, recent top set, 6-wk trend.
  • Volume — tonnage (Σ sets·reps·weight per movement): total work done. Per-session and per-week, 6-wk trend.
  • Plus frequency (sessions/wk). For bodyweight/conditioning moves, volume falls back to reps · distance · time.

They diverge usefully — volume ↑ with e1RM flat = building work capacity; e1RM ↑ with volume ↓ = peaking. The model reads the pair, not one number.

03

Feed the modelprogression + adherence

Two distilled blocks join the prompt. Progression is the computed summary above. Adherence is LLM-judged — the plan's semi-numeric prescriptions and Hevy's free-form names don't cleanly diff, so we hand both to the model and let it reason.

  • PLANNED: last block's sessions (reuse the archive read already in generateProgram.ts).
  • ACTUAL: the week's strengthSessions.
  • System prompt: progression → push/hold/deload; adherence → repeat/scale/adapt; recognise repeated swaps; never penalise missing history.

What the model receives

Adherence, judged not diffed

Rather than a brittle name-matcher, the prompt carries a compact planned-vs-actual view and asks the model to assess it — tolerant of "Squat (Barbell)" ≈ "Back Squat" and of a swapped exercise.

Design decisions

Why these calls

LLM-judged adherence

Prescribed reps/load are strings + free-text; Hevy names differ. The model tolerates that fuzziness; a matcher wouldn't. Minimal brittle code.

Two progression axes

e1RM (strength ceiling) and volume/tonnage (work done) move independently — tracking both tells the model whether you're getting stronger, doing more, or peaking.

Idempotent history

Sessions keyed by a hash of start-time, so overlapping weekly exports merge cleanly instead of double-counting.

Graceful absence

No Hevy data → prompt says "not tracked" and generation is unchanged. Never penalise the athlete for missing logs.

Distilled, not raw

Summaries into the prompt, not every set — keeps the ~4-min / paid generation from ballooning in tokens and latency.

Snapshot kept

current_lifts stays derived for backward-compat, so nothing downstream breaks while the richer path lands.

Verification

How we prove it

  1. Unit-test the analyzer (e1RM, PR, trend, session grouping) against the existing real Hevy fixture.
  2. Import a CSV → strengthSessions docs appear; re-import an overlapping export → no duplicates (idempotent).
  3. Regenerate → the prompt carries the progression + PLANNED/ACTUAL blocks; the program's currentState / coachNotes cite real trend + adherence.
  4. Graceful-absence: clear history → prompt shows "not tracked", generation unaffected.
  5. Watch prompt size / latency; trim summaries if the generation grows past its ~4-min budget.

Out of scope

Not in this pass

Sleep check-in (dropped for now) In-app set logging — Hevy owns it Real-time per-day auto-regulation Full analytics dashboard — screens surface just enough
Deviation handling comes for free: because Hevy already records what you actually did, a swapped or missed lift shows up in ACTUAL and the model reconciles it — no in-app logging, no penalty. The single decision that unlocks progression, PRs, and adherence together is Part 01: keep the history instead of overwriting it.
